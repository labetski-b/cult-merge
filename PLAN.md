# План разработки веб-версии CULT.MERGE

## 0) Цель документа

Этот план объединяет:
- выводы из `GAME_DESIGN.md` и `GAME_DESIGN_FINAL.md`;
- архитектурный фидбэк перед стартом реализации;
- список неясностей, которые блокируют точную реализацию;
- обновленный roadmap с критериями готовности.

Документ ориентирован на MVP веб-прототипа для быстрого баланс-тестирования.

---

## 1) Фидбэк в ролях

### 1.1 Архитектор (технический взгляд)

Что хорошо:
- Правильно выбран стек для быстрого цикла: React + TypeScript + Zustand + Vite.
- Баланс вынесен в данные, а не в код.
- Локальный save/load закрывает потребность MVP.

Ключевые улучшения:
1. Разделить доменную логику и UI.
   - Весь расчет мерджа, наград, прогрессии и задач должен жить в `src/domain/*` как pure functions.
   - React-компоненты должны быть только отображением и диспетчеризацией действий.
2. Зафиксировать единую модель состояния поля.
   - Не хранить отдельно `creatures[]` и `generators[]` с дублирующими координатами.
   - Хранить `entitiesByCell` + `entitiesById`, чтобы исключить коллизии и гонки при drag-and-drop.
3. Ввести версионирование сейва.
   - Формат: `{ version, savedAt, state }`.
   - Нужен мигратор, иначе каждое изменение схемы ломает старые сохранения.
4. Зафиксировать deterministic random для тестов баланса.
   - Для production можно `Math.random`, но для debug/QA должен быть seedable RNG.
5. Нужны инварианты уровня домена.
   - Нельзя иметь 2 сущности в одной клетке.
   - Нельзя мерджить невалидные пары.
   - Нельзя выполнить заказ, если ресурсы/существа не списаны атомарно.

### 1.2 Геймдизайнер (игровой взгляд)

Что хорошо:
- Core loop понятный: генерация -> merge -> заказ -> награда -> прогресс -> новые генераторы.
- Порог входа низкий, что хорошо для тестового полигона.

Что улучшить до старта разработки:
1. Уточнить экономику ранней игры.
   - Сейчас легко получить soft-lock по мясу при неудачном темпе.
   - Нужен fallback (например, бесплатное мясо по таймеру/кнопка в debug только для dev-режима).
2. Стабилизировать first-time user flow.
   - Первый заказ, первый merge и первый reward должны быть заскриптованы и предсказуемы.
3. Явно описать целевой pacing.
   - Сколько минут на LVL 1->3, 3->5, 5->7 в нормальном прохождении.
4. Проверить overflow экономики Eyes.
   - В MVP Eyes почти не тратятся, возможна инфляция и потеря смысла ресурса.

### 1.3 Продюсер/техлид (поставка)

Что хорошо:
- План уже разбит на MVP-этапы.

Что улучшить:
1. Ввести Definition of Done по этапам.
2. Добавить риск-регистр и блокеры по данным.
3. Сделать stage-gates: нельзя начинать следующий этап без закрытия критических вопросов по балансу.
4. Разделить "MVP для проверки петли" и "MVP для масштабного баланс-теста".

## 2) Противоречия и неясности (критично)

Ниже вопросы, которые нужно зафиксировать до реализации соответствующих модулей.

1. `expMultiplier` в примерах.
- В одном месте указано: `0 = стандартная награда`.
- В кодовом примере из плана: `exp = baseExp * (expMultiplier || 1)`.
- Нужно утвердить правило: `0` как sentinel или реальные множители (`1`, `2`, ...).

2. Стартовый заказ.
- В материалах фигурируют первые явные mandatory-заказы для Kraken LVL 2.
- В плане есть `getFirstMandatoryTask(1)`.
- Нужно утвердить, есть ли обязательный заказ на LVL 1.

3. Scope Random Tasks.
- В `GAME_DESIGN_FINAL.md`: random tasks отложены после MVP.
- В текущем плане: random tasks включены в MVP 2.
- Нужна единая фиксация границы MVP.

4. Mobile scope.
- В плане mobile-friendly есть в MVP 3, а в final scope mobile оптимизация отложена.
- Нужно утвердить: адаптив обязателен в MVP или нет.

5. EXP прогрессия Kraken.
- В старом документе есть вопрос: шаговые требования считаются отдельно или накопительно.
- В final это частично описано, но формула перехода между step/level должна быть зафиксирована как однозначный алгоритм.

6. Экономика Eyes.
- В MVP Eyes "в прогрессе, но не для покупок".
- Если ресурс не имеет sink, баланс по Eyes нельзя валидировать.
- Нужно зафиксировать роль Eyes на MVP: только telemetry-метрика или валюта.

7. Генератор 3 (Chicken).
- Отложен, но его наличие влияет на долгосрочную архитектуру таймеров и tick-системы.
- Нужно решить: закладываем абстракцию таймерных генераторов сейчас или откладываем полностью.

8. Источник файла с внешним планом.
- В рабочей папке отсутствует `delightful-drifting-sloth.md`.
- Если этот документ обязателен, его нужно добавить в репозиторий или дать путь для чтения.

## 3) Целевая архитектура MVP

### 3.1 Технологии (утверждено)
- React + TypeScript
- Zustand
- @dnd-kit
- Vite
- TailwindCSS (или простой CSS-модульный слой, если скорость важнее)

### 3.2 Слои

```text
src/
  app/            # bootstrap, providers
  ui/             # React components only
  domain/         # pure game logic
  store/          # Zustand state + actions
  data/           # JSON balance packs
  infra/          # save/load, rng, telemetry
  test/           # unit/integration fixtures
```

### 3.3 Доменные модули
- `domain/merge.ts` - merge rules + validation.
- `domain/generator.ts` - spawn logic + probability selection.
- `domain/tasks.ts` - task selection, validation, completion.
- `domain/rewards.ts` - EXP/Eyes/Rune calculations.
- `domain/kraken.ts` - level/step progression.
- `domain/runes.ts` - rune merge + redemption.

### 3.4 Состояние
- Единый источник истины для поля:
  - `grid: { rows, cols, cells }`
  - `entities: Record<EntityId, Entity>`
- Нормализованная модель, все мутации через actions.

### 3.5 Сохранение
- Автосейв после атомарных транзакций.
- Формат с версией и миграциями.

### 3.6 Тестирование
- Unit-тесты домена (обязательно).
- Минимум 1 интеграционный тест core loop (generator -> merge -> task -> level up).

## 4) Обновленный roadmap

## Stage A. Spec Freeze (1-2 дня)

Результат:
- `GAME_SPEC_MVP.md` с закрытыми критическими вопросами.
- Зафиксированный MVP scope.

Acceptance criteria:
- Закрыты все пункты из раздела 2 с меткой "критично".
- Есть однозначные формулы для rewards и progression.

## Stage B. Foundation (2-3 дня)

Результат:
- Проект поднят, слой домена и стор готовы.
- Загружены и валидируются JSON-данные.

Tasks:
1. Инициализация Vite + React + TS.
2. Настройка структуры слоев.
3. Подключение Zustand + persist + save versioning.
4. JSON schemas + runtime validation (`zod` или эквивалент).

Acceptance criteria:
- Приложение стартует.
- Некорректные balance файлы валятся с понятной ошибкой.

## Stage C. Core Loop Vertical Slice (4-6 дней)

Результат:
- Играбельный цикл на Generator 1 + mandatory tasks.

Tasks:
1. Grid + drag-and-drop.
2. Merge существ.
3. Зарядка генератора и спавн по вероятностям.
4. Выполнение mandatory-заказа.
5. Начисление EXP/Eyes, прогресс Kraken.
6. Автосейв/лоад.

Acceptance criteria:
- От нового сейва можно пройти минимум 10-15 заказов без soft-lock.
- После перезагрузки состояние полностью восстанавливается.

## Stage D. Economy Loop (3-4 дня)

Результат:
- Руны, сундуки, покупка/merge генераторов.

Tasks:
1. Res_Box открытия с вероятностями.
2. Rune merge + redemption.
3. Магазин генераторов и их merge.
4. Рост сетки по Kraken level.

Acceptance criteria:
- Можно купить второй генератор без debug-кнопок.
- Экономика воспроизводима под фиксированным seed.

## Stage E. QA + Balance Toolkit (2-3 дня)

Результат:
- Инструменты для быстрых итераций баланса.

Tasks:
1. Debug panel (ресурсы, уровень, skip task, reset save).
2. Логи телеметрии локально (в консоль/JSON).
3. Набор regression-сценариев.

Acceptance criteria:
- Любой параметр из `src/data/*.json` проверяется в игре за 2-3 минуты.

## 5) Risk register

1. Неполная или противоречивая балансная таблица.
- Митигировать: stage A spec freeze + schema validation.

2. Soft-lock экономики мяса.
- Митигировать: гарантированный fallback источник мяса в MVP.

3. Слишком раннее усложнение UI/анимаций.
- Митигировать: UI минимум до закрытия Stage D.

4. Поломка сейвов при изменении модели.
- Митигировать: versioned save + migrations.

5. Нестабильные баги вероятностей.
- Митигировать: seedable RNG + симуляционный smoke-тест.

---

## 6) Что непонятно по игре (для уточнения у геймдизайна)

1. Точное правило `expMultiplier/resMultiplier` и default значения.
2. Полный список mandatory tasks для ранней кривой (минимум LVL 1-10).
3. Условия появления random tasks и их вес/частота.
4. Полная таблица Kraken progression (шаги, EXP, награды) в одном источнике.
5. Жизненный цикл Eyes в MVP: где тратятся или зачем копятся.
6. Правило выдачи/восстановления мяса без debug-читов.
7. Статус стартового Egg: что из него получается и когда.
8. Ограничения по полю: что происходит при переполнении спавном.
