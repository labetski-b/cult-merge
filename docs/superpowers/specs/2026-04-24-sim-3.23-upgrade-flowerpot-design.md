# Симулятор 3.23 — async-апгрейды, Flower pot, reward-driven unlocks

Дата: 2026-04-24
Ветка: `sim-research-3.23`
Автор: orchestrator (labetsky)

## Контекст и цель

Симулятор CULT.MERGE работает с игровой логикой уровня релиза 3.22 (старая модель: `merge_cascade`, покупка генераторов за руны, нет Flower pot). В релизе 3.23 игра ушла вперёд:

1. Апгрейды генераторов стали **async single-slot с таймером и merge-gate** (а не мгновенный `merge_cascade`).
2. Появился новый генератор **Flower pot** — пассивный спавн по 30-минутному таймеру + чит «+30 минут».
3. Все генераторы **кроме Gen1** и Flower pot теперь **выдаются через награды** (kraken progression / boxes), а не покупаются за руны.
4. `generators.json` расширен с 5 до 10 уровней, каждый с инлайн-полем `upgrade`.

Цель работы: привести симулятор в соответствие с логикой 3.23, чтобы им снова можно было пользоваться для балансировочных экспериментов.

Ссылки:
- `docs/superpowers/specs/2026-04-23-generator-upgrades-design.md` — дизайн real-game апгрейдов, от которого отталкиваемся.
- `src/simulation/README.md` — текущая архитектура симулятора.

## Решённые в brainstorming вопросы (фиксация выбора пользователя)

1. **Scope**: делаем всё — async-upgrades, merge gate, rune cost, Flower pot.
2. **Время таймера апгрейда**: мгновенный collect (таймер игнорируется, важен только сам slot-lock и трата рун/мерджей).
3. **Время спавна FP**: фиксированный интервал тиков `FLOWERPOT_SPAWN_TICKS`, калибруется один раз по среднему wall-clock за тик (baseline run без FP).
4. **Quest-driven FP boost**: новое действие `flowerpot_cheat_time` (+30 мин ко всем FP). Стратегия использует его в цикле «чит → collect → merge-to-target-level → feed», пока квест на FP-существо не закрыт.
5. **Стратегия выбора упгрейда**: гибрид A+B. Приоритет 1 — генератор/FP, выдающий существо активного квеста. Приоритет 2 — младший unlocked с набитым merge-gate и доступными рунами.
6. **Обратная совместимость**: полный переход на новую механику. Существующие experiments (1-10) маркируем `DEPRECATED.md`, создаём новый baseline `11.sim-3.23-baseline`.

## Важное изменение: reward-driven unlocks

**Все генераторы и все FP приходят через награды. Ничего не покупается за руны, кроме упгрейдов.**

- Gen1 — стартовый, всегда в `unlockedGenerators` с первого тика.
- Gen2…GenN — выдаются через `claim_reward`/`open_box` (таблица наград в `kraken_progression.json` / `res_boxes.json`).
- Flower pot — аналогично, через награды.
- Руны (rune1/rune2) — единственная валюта; тратятся **только** на `start_upgrade` генератора или FP.

**Удалённые действия симулятора**: `buy_generator`, `merge_cascade`, любая попытка `buy_flowerpot`.

## Открытые вопросы (research перед написанием плана)

Эти пункты выясняет research-agent в первой фазе writing-plans. Их результат может повлиять на план, но не на общий дизайн.

1. **Слот `activeUpgrade`**: один общий для Gen и FP, или два раздельных? От этого зависит логика приоритетов в стратегии (конкурирующие кандидаты vs параллельные).
2. **Структура апгрейда FP** в `flowerpots.json`: есть ли поле `upgrade` на каждом уровне? Что играет роль `mergesRequired` (раз merge FP запрещён) — счётчик собранных спавнов, просто руны, cooldown-таймер?
3. **Таблица выдачи генераторов и FP** в `kraken_progression.json`/`res_boxes.json`: на каких уровнях кракена какой `genId`/`fp` выдаётся. Нужно симулятору, чтобы не планировать апгрейд ещё не разблокированного.
4. **Представление FP-item в inventory**: новый тип `FlowerPotInstance` vs переиспользование существующего inventory-узла.

## Архитектура изменений

### 1. State (`SimulationState`)

Новые поля:

```ts
// Async-апгрейд: один слот, таймер хранится, но в collect-логике игнорируется.
activeUpgrade: {
  targetType: 'generator' | 'flowerpot';
  entityId: string;            // generatorId или flowerpotId
  toLevel: number;
  startedAt: number;           // для метрик
  finishesAt: number;          // игнорируется стратегией (выбор B)
} | null;

// Merge-gate: сколько мерджей уже "потрачено" на апгрейды конкретного генератора.
// Available = totalMerges(gen) - mergesSpentByGen[gen].
mergesSpentByGen: Record<string, number>;

// Набор разблокированных генераторов. Стартует с {"Gen1"}.
unlockedGenerators: Set<string>;

// Активные Flower pots (могут быть несколько).
flowerpots: FlowerPotInstance[];

// Для метрик чит-ускорения.
flowerpotCheatBonusMs: number;
```

`FlowerPotInstance`:

```ts
type FlowerPotInstance = {
  id: string;                 // "fp_1", "fp_2", ...
  potLevel: number;           // 1..5
  lastSpawnTick: number;      // счётчик пассивного таймера
};
```

### 2. Новые actions (`SimulationAction`)

Добавляем в `src/simulation/engine/types.ts`:

| Action | Поля | Предусловия | Эффект | actionTime |
|---|---|---|---|---|
| `start_upgrade` | `{ targetType, entityId, toLevel }` | `activeUpgrade==null`, merges≥required, runes≥cost, entity unlocked | списывает руны, инкрементит `mergesSpentByGen`, ставит `activeUpgrade` | 0.5s |
| `collect_upgrade` | `{}` | `activeUpgrade!=null` | `level++`, `activeUpgrade=null` | 0.5s |
| `flowerpot_cheat_time` | `{}` | есть хотя бы один FP | `flowerpotCheatBonusMs+=30min`; немедленный forced-spawn всех FP; спавны автоматически попадают в inventory | 2s |
| `claim_reward` (расширение существующего) | `{ rewardType, payload }` | есть pending reward | rune/gen-unlock/fp-spawn в зависимости от `rewardType` | как раньше |

**Примечание**: отдельного `collect_flowerpot_spawn` нет. Пассивный и cheat-спавны FP кладутся в inventory автоматически из `SimulationEngine`. Стратегия работает с этими существами через существующие `merge`/`feed`.

**Удаляем**: `buy_generator`, `merge_cascade`, `buy_flowerpot` (последнего никогда и не было).

**Расширяем `merge`**: без изменений для креатур (FP не мёрджится, генераторы мёрджатся только для прироста `availableMerges` — результат этого мерджа больше не апгрейдит напрямую).

### 3. Пассивный спавн Flower pot

Обрабатывается в `SimulationEngine` после `strategy.decide()` в каждом тике:

```
for fp in state.flowerpots:
  if currentTick - fp.lastSpawnTick >= FLOWERPOT_SPAWN_TICKS:
    creature = rollFlowerPotSpawn(fp.potLevel, flowerpots.json)
    inventory.add(creature)
    fp.lastSpawnTick = currentTick
    metric('flowerpot_passive_spawn', fp.id)
```

Константа `FLOWERPOT_SPAWN_TICKS` задаётся в `src/simulation/engine/flowerpot.ts` с комментарием о дате и способе калибровки.

### 4. Стратегия (`RealisticStrategy`)

Phase machine расширяется: `task → reward → invest → upgrade → collect_upgrade → task`.

**Фаза `reward`**: обработчик `claim_reward` умеет выдавать:
- rune1/rune2 → `resources`,
- `generator` → `unlockedGenerators.add(genId)`,
- `flowerpot` → `flowerpots.push(new FlowerPot(potLevel=1))`.

**Фаза `task`**:
- Если активный квест требует существо, которое спавнит какой-то FP → переключаемся в quest-driven FP-loop: `flowerpot_cheat_time` → collect → merge to target level → feed. Повторяем, пока квест не закрыт.
- Иначе — обычный путь через генератор (charge → spawn → merge → feed).

**Фаза `upgrade`** (выбор кандидата):
1. **Quest-relevant**: кандидат, чей output совпадает с требованием **текущего активного квеста**, и бюджет (merges для Gen / `availableMerges`-аналог для FP) + руны удовлетворены.
2. **Youngest unlocked with budget**: если #1 не нашёлся, берём самый младший по уровню среди unlocked с выполненным бюджетом.
3. Иначе — skip, назад в `task`.

Про «ближайший квест» (look-ahead) явно не решаем в этом дизайне — только активный. Если практика покажет, что стратегия копит руны без цели — добавим look-ahead в отдельном pass.

Если слоты раздельные (открытый вопрос 1) — приоритеты применяются в каждом слоте независимо.

**Фаза `collect_upgrade`**: в первом же тике после `start_upgrade` собираем (таймер игнорируем).

### 5. Метрики и chart-агрегация

Новые метрики в `src/simulation/engine/metrics.ts`:

**Upgrade-группа**:
- `activeUpgradeEntity` (строка, нулабельная) — для timeline.
- `upgradesStarted`, `upgradesCollected` — кумулятивные.
- `mergesSpentByGen` — snapshot на тике.
- `idleUpgradeTicks` — пустой слот, когда можно было стартануть (sanity).
- `runeStarveRejects` — реджекты из-за рун.

**Flower-pot-группа**:
- `flowerpotCount`, `flowerpotLevels` (histogram по `potLevel`).
- `flowerpotPassiveSpawns`, `flowerpotCheatSpawns` — раздельно.
- `flowerpotCheatClicks`.
- `questsClosedViaFP`.

**Generators-группа (обновление)**:
- `unlockedGenerators` (snapshot).
- `generatorLevels` (snapshot).

Все метрики поддерживают 5 режимов оси X из `chartAggregation.ts`. Таблица видимости в `src/simulation/README.md` обновляется.

Dashboard (`src/simulation/main.ts`):
- Вкладка «Upgrades» — timeline `activeUpgradeEntity`, bar chart `mergesSpentByGen`.
- Вкладка «Flower pot» — `flowerpotCount`, split passive vs cheat spawns.

### 6. Калибровка `FLOWERPOT_SPAWN_TICKS`

Одноразовая процедура через `scripts/calibrate-flowerpot.ts`:

1. Прогон 10k тиков без FP → суммарный `actionTime` / ticks = `avg_tick_wallclock_sec`.
2. `FLOWERPOT_SPAWN_TICKS = ceil(1800 / avg_tick_wallclock_sec)`.
3. Записывается в `src/simulation/engine/flowerpot.ts` с датой и параметрами калибровочного run'а.
4. Повтор калибровки требуется только при существенных изменениях `actionTime` (отдельный раздел в README).

## Тестирование

**Уровень 1 — unit-тесты** в `src/simulation/__tests__/`:
- `upgrades.test.ts`: корректное списание рун/мерджей, все reject-ветки (слот занят, не хватает рун, не хватает мерджей), collect при пустом слоте, двойной start в одном тике.
- `flowerpot.test.ts`: passive-спавн ровно на `lastSpawnTick + FLOWERPOT_SPAWN_TICKS`, weighted-ролл (seeded, детерминированно), cheat форсит всех.
- `rewards.test.ts`: claim типа `generator`/`flowerpot`/rune — каждый эффект.

**Уровень 2 — integration через `run-sim.ts`** (assertion-хелпер после 50k-тикового прогона):
- Все Gen разблокированы не раньше своей позиции в `kraken_progression.json`.
- `mergesSpentByGen[gen] <= totalMerges[gen]` всегда.
- `activeUpgrade` не висит >100 тиков (stuck detector).
- Quest completion rate ≥ зафиксированного baseline 3.23.

**Уровень 3 — regression snapshots**: `src/simulation/__tests__/snapshots/baseline-3.23.json`. Отклонение >5% по ключевым метрикам (`totalEyes`, `krakenLevel@50k`, `chapterReached@50k`) требует явного обновления snapshot и объяснения в commit message.

## Risks / что мониторим во время implementation

- **Дрейф baseline 3.23**: если quest completion rate падает >10% от релиза — останавливаемся и разбираем почему (стратегия / баланс данных).
- **Slot starvation**: если `idleUpgradeTicks` > 30% — приоритеты стратегии слишком строгие, нужен fallback.
- **FP cheat abuse**: если `flowerpotCheatClicks` на порядок больше естественного темпа → стратегия зациклилась, нужен cooldown/cap.
